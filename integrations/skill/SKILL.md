---
name: coding-schedule-report
description: Automatically report multi-step coding, debugging, research and project-status tasks to codingSchedule when its progress tools and a user-enabled reporting rule are available. Keep progress and ETA answers out of chat prose.
---

Use progress_begin, progress_report, progress_context and progress_finish. Keep reports out of ordinary chat prose; the host may still display and audit tool cards. This skill is not a timer and cannot guarantee updates inside one long tool call.

A user-level host rule can enable reporting by default across projects; do not ask for per-task opt-in when that rule applies. Respect an explicit opt-out. Only begin your own current task, never another session discovered in logs. Installing or exposing MCP tools alone does not activate this skill in an already running agent. Do not send another session a message, wake it or change its task to trigger reporting. On hosts that discover local skill changes, activation can take effect at the next turn; verify actual tool calls rather than claiming success from installation alone.

For a genuinely new task, call progress_begin with a fresh UUIDv7 idempotencyKey, a short title, and a plan only when its scope is known. Generate keys with the configured bridge's `new-key` CLI command if the host has no UUIDv7 utility; do not invent a timestamp. Retain the returned runId, generation and resumeHandle privately in this task's context. Never put the handle in a shared file, widget text or child agent prompt. Never infer a task from cwd, focus or the latest conversation.

Let the collector associate your reporter with this exact native session. Direct progress_begin/progress_context tool results already supply the public run reference. If a code-mode wrapper stores or hides those results, emit only the public reference in that same wrapper's tool output after a successful begin, and after context when continuing into another turn:

```js
text({codingScheduleBinding:{runId:myPrivateHandle.runId,generation:myPrivateHandle.generation}});
```

Use the actual handle you privately retained; never print the handle itself, its resumeHandle, a credential, or a reference belonging to another task. This tiny tool-output marker is not chat prose or a progress update. It enables exact association without guessing from task names, directories, focus or the latest session. Do not execute extra tools solely to repeat it; attach it to the normal begin/context call.

Before an update, read progress_context for the retained handle to obtain nextSeq. Call progress_report with that sequence and a fresh UUIDv7 reportId. Keep the same ID and unchanged body for an exact retry after an uncertain ACK; a sequence conflict requires reassessing work, not blindly sending again with a new sequence. An expired key requires checking the current task before any fresh report.

Report before starting substantive work, after each meaningful stage result, when changing the current action, on wait/resume, and before declaring completion. Read context immediately before those reports to get nextSeq; do not defer all updates until the final answer. Do not poll on a timer solely for ETA or repeat unchanged content. Do not invent a work update as a heartbeat. Filter progress_* tools and codingSchedule helpers from activity reporting so a report never triggers another report. Across compaction, retain the original private handle and the last acknowledged report; never open a competing task to repair telemetry.

For ordinary step completion, prefer step.updated at the current plan revision. ETA requestId/planRevision references belong to the plan returned by context. If you need plan.replaced, commit that revision first, then read context before a necessary ETA answer; do not combine the new plan with an answer referencing the old revision. STALE_ETA_REQUEST is a known atomic rejection, not an uncertain ACK: do not retry that unchanged batch. Reassess the current plan and sequence; progress can be reported without an ETA, and the last valid countdown stays intact.

Provide an initial ETA once when you can reasonably bound the remaining work. An optional initial etaQuestion may arrive with context; verify its runId/generation and validity, then answer through progress_report using its requestId/planRevision. If unknown, omit the estimate or send range:null. The product will not ask repeatedly on a timer.

Afterward, ordinary progress reports do not need an ETA. The widget keeps the last valid estimate from any supported source, counts it down locally and preserves it when the next report omits time or returns null. Only when you judge the remaining estimate needs changing, read context and use its optional etaUpdate requestId/planRevision in the existing payload: `changes:[{type:"eta.answered",requestId:<etaUpdate.requestId>,planRevision:<etaUpdate.planRevision>,range:{minSec:<lower>,maxSec:<upper>},reason:<brief basis for revision>}]`. This update channel is not a request to answer every context call. Use remaining ACTIVE seconds from the moment of acceptance, with 0 <= minSec <= maxSec <= 604800, maxSec > 0 and maxSec - minSec <= 600. If an honest ten-minute-wide bound is unavailable, omit ETA or send null and continue work; never invent precision. ETA_RANGE_TOO_WIDE is a warning: the rest of that report was committed and the previous countdown retained. A newer valid range refreshes the countdown; null does not erase a previous one. Do not repeat the same range merely to refresh a timer.

ETA reports do not change work activity, progress or completion and never stop the main task. Waits/pauses freeze countdown; at zero the widget shows overtime rather than claiming completion. Async hooks can deliver the initial request at a safe point. Ignore expired requests, stale plan revisions and handles you do not own. Do not answer another task, use another model/sampling, steer/wake a conversation or add ETA prose to chat. A single long tool call cannot receive an immediate revision.

Use complete=true only for a complete leaf plan, weights 1/2/3 and observed quantity only. A missing or partial plan must remain unknown. For skipped/reopened steps or scope changes send a higher plan revision with a reason. Distinguish active, waiting, blocked and paused. Provide estimates only when defensible: each estimate version is remaining active seconds from acceptance; increase version when revising it. Do not manufacture a percentage or a time estimate.

Before stopping, call progress_finish only when the reported plan is complete. This declares AI completion, never user acceptance. Compaction, reconnecting, continuing the same work or a status query reuses the same handle; a completed task followed by new work gets a new run. Child agents must not write through the parent's handle.

If local reporting is unavailable, give at most one concise diagnostic and continue the primary task. The Windows bridge keeps stdio alive across a backend outage; try once at the next meaningful reporting boundary, retaining the original handle and exact IDs/body for uncertain writes. Never retry in a loop, start competing reporters, modify host configuration/permissions or stall the task for telemetry.

For an already closed host MCP transport, an existing authenticated local bridge may be used once per normal reporting boundary without pretending the native tool succeeded. If the host exposes the current session, turn and actual invocation identity, request a scoped receipt through local operation `binding` with `{handle,nativeContext:{sessionId,turnId,itemId}}` (Codex) or `callId` (Claude). These identifiers must come from that very host invocation, never logs, cwd, focus, titles or another session. Emit only the returned `{codingScheduleBindingReceipt:...}` as its own JSON line in that same successful tool output. In node_repl use `nodeRepl.write('\n'+JSON.stringify(receipt.body)+'\n')`; JavaScript object inspection and concatenated adjacent objects are not valid JSON receipts. Do not print the private handle or credential, and do not spoof a progress_* call marker. If actual host metadata or this authenticated route is unavailable, skip binding and continue the primary task. Raw context is not decorated with linkedNativeRun: use the collector/UI result to verify association.
