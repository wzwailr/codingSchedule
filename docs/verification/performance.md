## 资源门槛与负载

2026-10-29 的三 MCP 实例修复和重测见[当前记录](multi-mcp-endurance.md)。下文各 v4 结果均为历史单 MCP 负载。

同日进一步核查发现：旧采样器只求指定PID，遗漏控制台程序生成的conhost子进程。旧表格保留当时数值，但其中“全部进程”的口径需按这一更正收窄，不能继续用作完整进程树的验收。新采样器枚举全部后代并求和；v10转发器使用Windows子系统与继承的stdio管道，不创建控制台。实际MCP往返和无conhost的反例回归另有RED/GREEN记录。

正常五分钟：10 个 reporter 任务、合计 20 事件/秒，另加原生日志混合源；有效报告发出至 renderer animation-frame 接收 P95 ≤1000ms，日志追加至同一渲染接收点 P95 ≤3000ms；产品进程树 Private Bytes ≤220MiB，正常平均 CPU ≤整机容量 3%，另测 5 分钟空闲 CPU ≤1%。用户于 2026-10-27 确认八小时耐久使用 2 事件/秒、10 个活动任务，保留 100MiB 有效数据库预算；末小时与第二小时内存中位差 ≤20MiB。

当前 v8 计入主进程（含 collector Worker 与共享 MCP SDK）、renderer、GPU、Network Service 和三个常驻 Win32 MCP 转发器；早期记录只计一个独立 Node MCP bridge，不能外推为多实例通过。早期 utility collector 为独立 PID，同样计入。不计基准 Node、PowerShell 采样器、AI CLI 和其他应用。Private Bytes 用 Windows Get-Process 的 PrivateMemorySize64；工作集另报，不能代替私有内存。CPU 取产品进程累计 CPU 增量除以墙钟时间和逻辑处理器数。

计时起点在发送前，包含本地网络和驱动调度，因此比 collector 收到事件更早。renderer 的公开快照订阅经 requestAnimationFrame 回传作为终点，**不等于物理像素呈现或原生输入验收**。窗口仅展示一个选定任务，其他任务的状态仍接收；高突发时每批五个事件合并成一次最新动作，逐条 COMMIT 数量另查 SQLite，不能由 UI 样本数推断无丢 ACK。

## 已获得的诊断

首个标准回放在约 250 秒时因外部 PowerShell 采样进程超时而中止，保留 `failure.json`，不能记为五分钟通过。中止前私有内存约 350–420MiB，已超过门槛。采样驱动改为常驻 PowerShell，失败仍非零退出，不把采样失败当作零 CPU。

五秒空闲对照仅用于定位：默认约 322MiB，`--disable-gpu` 约 255MiB，关闭 GPU 加 32MiB JS 堆参数约 260MiB。三种均超门槛；没有将实验参数写入产品默认设置。GPU/renderer/collector 均有成本，不能归咎于单个 UI 控件。

源码随后减少每次请求的凭据扫描，并避免无关任务更新导致选定任务 DOM 重建，两者都有真实失败回归再修复。完整新构建复测结果在后续记录，不能从这两项优化直接推定达标。

## 审阅后的采样完整性

标准门禁要求至少 10 个任务、全部 reporter 恢复 active、请求负载至少 20 事件/秒、实收事件数达到所请求时长的目标。资源每 5 秒采样，每个阶段至少 80% 的计划样本数，跨度覆盖该阶段减 15 秒，最大空洞及首末边界缺口不超过 15 秒，时间严格递增。任一项缺证即失败。进程启动到可见窗口的测量也按 3 秒门槛判定，包含驱动连接成本，不是重启系统后的冷磁盘缓存。

等待恢复、重复、乱序和新 MCP 连接场景在正式计时前完成，避免控制请求挤占同连接 20 请求/秒的令牌预算而悄悄降低负载。正常与突发计时段仅计活动事件；生命周期控制事件另核对 SQLite。上一轮因不同 run 的等待恢复而终止的采样标为无效负载，不纳入通过结果。
